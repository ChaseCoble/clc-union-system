### Architecture Decisions Carried Forward

A few things worth recording because they drove implementation shape.

**Urgency never leaves the backend.** It is computed, stored, used for scheduling, and stripped before any API response. `UrgencyStripRule` is always the last rule in the pipeline precisely because it would be incorrect to strip it earlier — rules upstream of it depend on it. The field is set to `None` on task objects after the pipeline runs, before serialization. It never appears in any response schema.

**Recompute takes a task list as input, never queries the DB directly.** This is the V2 compatibility constraint. When the orchestrator event bus exists, recompute will be callable as a pure function without a DB handle. The implementation enforces this now so the refactor is minimal later.

**Rules are a registered list iterated by the engine.** Each rule is a function decorated with `@register`. The pipeline runner iterates `_REGISTERED_RULES` in order. Adding a rule means writing a function and decorating it — nothing else moves. The `PlatformRotationRule` specified in the architecture doc is stubbed as a gap: it appears in the spec table but was not implemented in this pass because platform tracking requires session state that isn't threaded through the context yet. It will be added in V1.3.1.

**SessionManager is a class with a defined interface.** V2 will swap the health signal transport from direct function call to event bus publish. The interface doesn't change — only the transport inside `emit_signal`. This was designed in from the start.

**`queue_tier` column added before first migration.** HOT/COLD pool is a V2 data dependency. The column is nullable and present in the initial schema so V2 doesn't require a migration that touches existing data.

### Implementation

**Models:** 8 tables — tasks, platforms, task_artifacts, sessions, health_events, rules, rule_log, hyperparameters. Difficulty is computed from enjoyability × work_type via a lookup table and is never stored. Urgency_base preserves original user intent; only the user reduces urgency, automation only increments upward.

**Rule pipeline:** 7 rules registered in order. BlockFilter, ModeFilter, Aging (top_n_cycles tracking), BucketSlot (MLFQ enforcement), DifficultyAlternation (sliding window ceiling + step constraint), Enjoyability (DREAD hard rule with forward scan for ENJOYABLE), UrgencyStrip. The EnjoyabilityRule scans forward in the task list when a DREAD task is encountered and no ENJOYABLE task immediately follows — it swaps the nearest ENJOYABLE task into position rather than just dropping the DREAD task or breaking the rule.

**Aging:** Separate from the rule pipeline per the V2 interface spec. `aging.py` owns the formula: `aging_rate * (due_date_weight + time_in_system_weight + top_n_weight)`. Sweeps run on session activation and on the `aging_sweep_interval` hyperparameter timer. Due date weight is a step function; time in system is linear capped at 30 days; top_n is capped at 1.5.

**Health engine:** Signals emitted via direct call in V1. Interface is defined for event bus swap. Performance score formula: `clamp(task_points + active_minutes*0.1 - break_overage*0.5, 0, 100)` with a dread completion bonus of 10.0 per task.

**Hyperparameters:** All stored as rows, cast to float on read. 13 defaults seeded by the initial migration. Adjustable at runtime via `PATCH /api/hyperparameters/{key}`. No hardcoded values in the rules engine — everything reads from the hyperparameter table.

**Auth:** Independent JWT validation against the orchestrator public key. Service stays functional through orchestrator downtime. Intake endpoint uses a static bearer token — different auth path than user-facing routes.

**Initial migration:** Writes all tables and seeds platforms (HackerOne, Bugcrowd, BTLO, HTB, FHSU, Manual) and all hyperparameter defaults in a single migration. Platforms are data — no enum columns anywhere.

### Deployment Issues

**Port not exposed.** Container came up on `union_network` but no `ports:` mapping in the original compose file. Added `${SERVICE_PORT}:${SERVICE_PORT}`.

**Duplicate env var.** `.env` template had `PUBLIC_KEY_PATH` defined twice — once as the container-internal path, once overwritten with the host path. The app read the host path, looked for it inside the container, failed. Fixed by separating `PUBLIC_KEY_PATH` (container-internal, what the app reads) from `HOST_KEY_PATH` (host path, what compose uses for the volume mount source).

**Compose volume line truncated.** The original generated compose file had the key mount line cut off mid-string, so the key was never mounted at all. Fixed and verified.

**Pydantic ClassVar.** `VALID_SIGNALS` on `UserReportRequest` was a bare class attribute on a Pydantic v2 model. Pydantic v2 requires `ClassVar` annotation for class-level constants that are not model fields. One-line fix.

**Data directory.** `/srv/union/data/task-management` did not exist. Created before container start.
