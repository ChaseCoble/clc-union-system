Docker ingestion Architecture

First Iteration:
	Primary Threat Model: Docker Registry Corruption from User Error and Escalated User Privileges due to large access service
	Resulting Architecture: Systemd that utilizes the registry api to populate the supply chain and automatically create the SBOMs. Logging is present, with higher alerts for dupes caused by updating. Backups kept of both the json and the registry itself. The service will utilize a service user with whitelist only permissions and write protection on the script to prevent an automation script exploit being introduced. Specialized user has no permissions other than FACL permissions for relevant files. 

==A Note on the included script: I have included a dummy script because systemd/cron services require hard coded paths. The included script has redactions, the operative script is .gitignored==


Second Iteration:
	Prequisite: Systems Health Service
	Primary Threat Model: Docker Registry Tampering
	Primary Availability Concern: Free up polling resources by having a webhook trigger sync
	Resulting Architecture: In lieu of quiet logging, systemd flags the Systems Health Service for confirmation before adding dupes to the registry and the supply chain. The user identifies whether it is legitimate. Systemd is triggered by a webhook from the docker registry

Third Iteration:
	Prequisite: Database the source of truth, Activity confirmation service (Orchestrator knows when privileged user is actively monitoring dashboard)
	Primary Threat Model: Docker Registry Tampering and Supply Chain Compromise
	Resulting Architecture: Systemd checks current database of CVE and Vulnerabilities, as well as whether privileged user is active. If there are exploits, confirmation is required from user. If the privileged user is active, an alert is sounded for duplicate entries (indicating a user error or update) but the action continues. If user is not active, confirmation is required for next session and the job is queued.

### Alembic Issue
- Alembic is used for database migrations (changing the schemas in the database). It autogenerates the scripts to change the database non-destructively. 
- The issue I introduced was that alembic inside the container became decoupled from alembic in the dev directory. As a result, systems were not properly propagated between the two. 
- Solved by adding an additional mount to the container between the alembic folders so versioning stays consistent.

### Dashboard Backend
So, the way the dashboard itself is build, is that it is built once on dashboard infrastructure changes, and the backend serves the files statically. Since dashboard only really manages UX, and panels are sent wholesale from orchestrator, this makes the backend thin. With the static offering, that offers up the concern with dirbusting into the api files. This was evaluated and found to be a non-issue, since any files surfaced would be the same you could evaluate with DevTools or similar.
Since auth goes through dashboard backend, and then orchestrator backend, this caused a synchronization error between the two. Since a JWT token was involved (which are large), the dashboard kept getting internal server errors from httpx timeouts. I was able to fix this by explicitly setting time outs for the auth path, and giving ample time for read functions. The key symptom that surfaced that the JWT token was a core issue, was that incorrect logins were correctly handled, while correct ones were not.
