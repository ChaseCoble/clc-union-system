## Focus: Dashboard Frontend + Task Management Spec

### Login Break — Root Cause and Fix

Returning to the dashboard after time away, the frontend was rendering but login was failing with a 405 Method Not Allowed. Browser inspection revealed the frontend was loading a stale cached JS bundle that was still calling `/auth/login` instead of the correct `/api/auth/login`.

The `/api/` prefix is a deliberate security boundary — anything under `/api/` is auth-protected and rate-limited, making dirbust enumeration easier to detect and block. Non-prefixed routes are user-facing and evaluated individually.

After correcting the endpoint and rebuilding the static bundle, a second issue emerged: the dashboard and orchestrator containers were on separate Docker networks (`dashboard_default` and `orchestrator_default`). Docker's internal DNS only resolves service names within the same network. The fix was creating a shared `union_network` and attaching all Union services to it. This is now the standard — every Union service container joins `union_network` at startup.

With networking resolved, the orchestrator's database was not being found because the container volume mount was pointing at the wrong path. Once corrected, login succeeded, JWT was issued, cookie was set, and auth/verify passed. Dashboard shell is functional.

### First Panel: Task Management Service

#### Role

Manage a prioritized queue of tasks from multiple sources — HackerOne, Bugcrowd, BTLO, HTB, FHSU, and manual entry — for focused cognitive execution. The queue surfaces the right task at the right time given current cognitive availability and workload.

---

#### Architecture: Rules Engine on a Multi-Level Feedback Queue

The queue algorithm is a pipeline of discrete, replaceable rules — not a monolithic function. Adding or changing scheduling behavior means adding or modifying one rule. Nothing else moves.

**MLFQ Structure**

| Bucket | Label | Slots/cycle | Purpose |
|---|---|---|---|
| 0 | Urgent | 8 | Highest priority |
| 1 | Normal | 5 | Standard work |
| 2 | Low | 2 | Background tasks |
| 3 | Maintain | 1 | Always surfaces — nothing starves |

**Urgency vs Bucket — Key Separation**

These are related but independently mutable values.

- `urgency` is the anchor. Set by the user via priority label at task creation. Stored alongside `urgency_base` which preserves the original user intent.
- `urgency` can be incremented upward by automation (due date approach is the first planned trigger). Only the user can reduce it. Automation never reduces urgency — it only escalates.
- `bucket` is the current queue position. Derived from urgency at creation, then drifts independently via aging, manual promote/demote, and rule engine decisions.
- A task can have low urgency but high bucket due to aging. A task can have high urgency but a lower bucket if manually demoted. They are not locked together after creation.

**Rule Pipeline**

Rules execute in sequence. Each receives the output of the prior rule.

1. BlockFilterRule — remove blocked tasks
2. ModeFilterRule — filter by work type against current mode
3. AgingRule — promote tasks overdue for surfacing
4. BucketSlotRule — fill slots per bucket weights
5. DifficultyAlternationRule — avoid consecutive Hard tasks
6. EnjoyabilityRule — apply adenosine cost rules
7. PlatformRotationRule — no more than 2 consecutive same-platform tasks
8. UrgencyStripRule — strip urgency from output, always last

---

#### Mode

Mode reflects cognitive availability — what kind of work can be engaged with right now. It is not a measure of urgency. Mode is a filter applied at queue request time. It does not trigger a recompute.

| Mode | Surfaces | Context |
|---|---|---|
| Deep-Work | All work types | Full attention available, uninterrupted |
| Light-Work | Light-Work, Phone-Work | Available but may be briefly interrupted |
| Phone-Work | Phone-Work only | After hours, caregiving context, phone only |

Mode is owned by the Task Management Service in V1. It will be promoted to the orchestrator when a second service needs mode awareness.

---

#### Enjoyability

Enjoyability is an adenosine management tool. Certain tasks carry a cognitive cost beyond their estimated time. The rule engine uses enjoyability to prevent consecutive high-drain tasks from collapsing the work session.

| Level | Description | Adenosine cost |
|---|---|---|
| Enjoyable | Genuinely excited for this task | Low |
| Pleasant | Enjoy it but not excited | Low-moderate |
| Neutral | No mood effect | Moderate |
| Difficult | Stressful or intimidating, requires push | High |
| Dread | High stress, significant drain, avoidance risk | Very high |

**Hard rule:** A Dread task is always followed by an Enjoyable task. No exceptions. The rule engine enforces this regardless of urgency or bucket.

---

#### Intake Contract

`POST /api/tasks/intake` is stubbed now as the defined entry point for external panel task submission. In V1 it functions as an alternate task creation endpoint. In V2 the orchestrator event bus calls it when any panel publishes a `tasks.ingest` event.

Service auth on this endpoint differs from user auth — service tokens carry `role=service` rather than `role=user` or `role=admin`. The orchestrator issues service tokens to trusted containers at startup.

---

#### Automated Urgency

The only automated urgency calculation planned for V1 is due date proximity. As a task's block_until date approaches, urgency increments upward automatically. All other urgency automation is deferred to future rule additions.
